# Candidate delegation input preparation

This is a private candidate for the unreleased `taskSource` / `delegation_input_contract` platform capability. No minimum client version or release pin is claimed. The structural projection v1 only requires fields/shapes; it is not equivalent to the original TaskSpec schema and does not prove permission, semantic completeness, real execution, or a business pass.

Lead owns `scripts/prepare_delegation_input.py`. Run it with Lead's authorized Python (standard library only); never run Evidence's interpreter. Each `--request`, `--assignment`, `--spec`, `--preflight`, `--execution-receipt`, `--authority` takes an explicitly authorized original file path and its independently expected full SHA-256. The helper never opens paths discovered inside those files. `--target-agent-id` is the current verified target identity, not a fixed release UUID; `--role` is the semantic role. `--output-directory` must already exist and be explicitly authorized; `--output-name` is a new ASCII version stem (letters/digits/underscore/hyphen, maximum 80 characters). The helper creates no directories. Outputs are `<stem>.task.json` and `<stem>.manifest.json`.

Branches:
- `--kind lead-request --role lead`: request and assignment only. Entry does not require a specialist TaskSpec before Lead can organize the request.
- `--kind metadata-preflight --role evidence`: request, assignment, complete pending Spec and independently prepared authority. This finite branch performs only the existing public read-only checker preflight, not specialist business or recursive preflight. Evidence uses its own verified runtime and emits the actual existing checker result and actual invocation/exit receipt.
- `--kind business --role <specialist>`: request, assignment, complete reviewed Spec, actual checker JSON output and a file binding to the actual execution receipt. Assignment scope/resources/Plan/delivery must equal Spec values. The source digest and result.spec_sha256 must match. A fabricated pass file can satisfy consistency and structure: these tools cannot authenticate execution; independently read the actual tool/run receipt and match the checked source/command/output/exit before dispatch.

Assignment JSON has exactly `role_task`, `io_scope`, `resources`, `parent_plan`, `delivery_requirements`. These use existing TaskSpec meanings; include all task-required current resources (including role-owned interpreter, reviewed lock and actual initialization receipt when required). Metadata assignment describes Evidence's checker scope/runtime, not the future business callee's runtime. Request text is read as exact UTF-8 bytes; full parsed Spec and full checker result are embedded without dropping fields. Source hashes refer to original bytes, not reserialized values.

On success, use `<stem>.manifest.json.taskSource` unchanged with the actual supported Delegate sync/async action and verified target. Do not also send `task`/`context`, retype or summarize the JSON, use SendMessage as a dispatch fallback, or use unsupported worker/subtask/handoff/resume source paths. Parallel independent role tasks retain separate generated files and owned output directories. Any control/recovery action must follow the actual current ToolCatalog; this helper supplies no bypass.

Inputs/output task are capped at 256 KiB each, BOM/NUL/invalid UTF-8/duplicate JSON keys/nonfinite numbers are refused. Current helper requires POSIX safe-open flags, exact absolute paths, regular single-link files, no symlink directories or traversal. It rechecks explicit source hashes before publication, but cannot take an atomic multi-file snapshot or authenticate caller permissions. Existing output task or manifest files are always refused (including an identical retry): choose a new version stem, never overwrite. The directory is held by descriptor, files are created with exclusive opens and held until path identity and bytes are rechecked. A failed operation preserves any partial files. Two-file output is not atomic; a manifest left by a failed operation is not a successful preparation receipt. Only a successful helper return after verification is usable, and same-OS-rights writers can still modify files afterward; consumers must verify hashes again. The manifest does not hash itself. The helper does not install, contact networks, execute checkers, delegate, or grant access.

Keep the existing Skill/TaskSpec substantive checks and raw evidence. Shape admission is neither actual execution nor a production-ready claim. Direct human requests remain governed by existing authorization. Existing `accepts_messages` and `accepts_handoff` settings are unchanged by this candidate; they are not aliases for an input contract and may expose other communication workflows. Review platform coverage and real runtime behavior before publication, not by assuming that adding a contract secures every channel.

Current Entry enters Lead with team-aware handoff(task/context), which taskSource does not support. Lead configuration is design-only and must not be activated; direct human Lead/maintenance paths stay unchanged. Keep specialist accepts_messages enabled: ordinary Delegate, fanout and resume also use this gate, so disabling it is not a SendMessage-only control. Disabling specialist accepts_handoff is a separate candidate policy; it does not gate ordinary Delegate or governed SendUserMessage returns, but this candidate does not change those settings and real runtime acceptance is still required.

SendMessage remains an unclosed programmatic entry in the inspected platform baseline; do not claim universal enforced dispatch admission until platform refusal coverage and real tests establish it.
